# Clone the Checkout, Lease Managed Slots, Budget Editors by RAM

The most usable tool is still a small, daemon-free CLI (working name `upool`) that keeps a per-project pool of persistent, pre-warmed git worktrees, leases them to agents, and keeps one machine-wide ledger of running Unity Editors; but the three-round spike on a 64 GB M1 Max (macOS 15.7.3, Unity 6000.4.11f1, Unity CLI 1.0.0-beta.13, Claude Code 2.1.295 inside desktop app 2.31226.1) moved three of v1's foundations (spike §1). Slots now live in Claude Code's managed directory, `<repo>/.claude/worktrees/slot-N`, not beside the repository as v1 argued: it is the only location where the desktop app grants a hook-made worktree auto-trust and its config overlay, the app hands a slot out in about 75 ms and never deletes one, and its garbage collector left a registered slot alone across two relaunches (spike §9 E.5; spike §9 E.7; spike §10). Slots are made by cloning the whole checkout, not by `git worktree add` plus a Library clone: a plain checkout costs 1.4 GB per slot and loses every gitignored agent file, whereas an APFS clone of the working tree costs 26 s and 47 MB, leaves `git status` clean, keeps mtimes so nothing recompiles, and carries `CLAUDE.md`, `AGENTS.md`, `.claude/` and `.agents/` along (spike §2 T1 extra; spike §2 TA). The Library story holds with first-hand numbers: `cp -cR` of a 6.3 GB, 91k-file Library takes 15 s and no disk; a cold open costs 235 s, 12,736 imports and 3.8 GB; the first open of a cloned slot at a new path costs 38 s with 0 to 1 imports and every later open 10 s, so a persistent slot costs about 0.4 GB (spike §2 T1.3; spike §2 T4; spike §3; spike §4). The sharp edges are measured too: a hook script must live outside `~/Documents`, because the desktop app runs `WorktreeCreate` through a `disclaimer` helper that cannot read a file there (a binary there runs, so upool is its own hook command; #163); subagent worktree requests never receive a `WorktreeRemove` and must not get pool slots; `UNITY_PROJECT_PATH` is honoured by `command`, `status`, `recompile`, `list`, `job`, `mcp` and `open` but ignored by `test`, `run`, `build`, `close` and `cache key`; `unity close` discards unsaved scenes silently; and `max_editors` becomes a RAM budget (about 2.5 GB per Editor plus 2 GB of helpers, three at 64 GB), because the concurrent cold imports that crashed a 15 GB Windows box merely ran 10 % slower here (spike §2 TB; spike §9 F.3; spike §8 B.3; spike §8 C.4; spike §2 T5.5). Set-up is one `upool init` per project; build the pool core first, the three-branch hook second, Editor governance third, and leave out daemons, GUIs, orchestration, scene merging and self-update.

## One binary, a dozen commands, one JSON file per pool

Every surviving tool in this niche is explicit about what it refuses to be: treehouse advertises "**No daemon** - all operations are inline CLI commands," warmtree is "Standard library only" and handles "only create and release," and the one documented regret in the space is a blanket `--force` that "overrode every protection at once" ([treehouse README](https://github.com/kunchenguid/treehouse); [warmtree on PyPI](https://pypi.org/project/warmtree/)). The Unity CLI is the counterexample on scope: its self-update and seven install channels generated fixes in three consecutive betas, and the spike itself opened with a `unity self-update` from beta.12 ([Unity CLI release notes](https://docs.unity.com/en-us/unity-cli/release-notes); spike §2 Setup 2). `upool` therefore owns exactly one lifecycle, acquire, govern, release a warm Unity workspace, and composes with git, the Unity CLI and Claude Code for the rest.

| `upool` does | `upool` does not |
|---|---|
| Create slots by whole-checkout APFS clone under `<repo>/.claude/worktrees/slot-N`; lease, refresh, reset and prune them | Run a daemon, GUI, database, MCP server or orchestrator |
| Keep a machine-wide ledger of running Editors under a RAM budget; serialize cold imports | Install Editors, manage licences, or sample `memory_pressure` (92 to 93 % free under 12.5 GB of Editor RSS) |
| Serve a registered project's Claude Code sessions a pool slot and its subagents a throwaway worktree, from hooks the project registers | Hand pool slots to subagents, or rely on Claude Code to remove anything |
| Export `UNITY_PROJECT_PATH` and pass the project path positionally on every Unity call it makes | Merge scenes, review code, plan tasks, or auto-commit work in progress |
| Mirror the gitignored files a project's `.worktreeinclude` names into the free slots before each handout (A44); revert define-order noise; park dirty slots | Write executables into repositories, or run any from them: the hooks `init` registers run upool itself |
| Register upool's hooks per project, in `upool init` (A26), and give a slot's sessions upool's instructions as the hooks' context, writing nothing into the project's agent files (A43) | Touch a repository `init` has not registered, or the user's own Claude Code settings (a committed `.upool.toml` is optional) |
| Register Unity projects with `upool init`; report what `unity vcs doctor` finds, and run `projects verify` at release (contracts.md A34, A35) | Self-update (defer to `brew upgrade`) |

The command surface copies the conventions the pool tools converged on: an acquire verb that prints **only the absolute path on stdout**, a release verb that resets the slot, `--json` everywhere, and side-effect-free `which`/`path` commands for agents whose cwd resets between tool calls ([treehouse README](https://github.com/kunchenguid/treehouse); [dcrousso/worktree-pool](https://github.com/dcrousso/worktree-pool)). Exit codes and the JSON envelope mirror the Unity CLI's own ([Unity CLI reference](https://docs.unity.com/en-us/unity-cli/unity-cli-reference)). The only additions since v1 are a `--confirm` phase on `take` and an agent-worktree collector folded into `prune`, both forced by measured Claude Code behaviour.

| Command | What it does |
|---|---|

| `upool take <name> [--base REF] [--lane script\|scene] [--holder ID] [--timeout S] [--no-create] [--json]` | Leases a ready slot, or clones one (26 s) up to `max_slots` unless `--no-create`; prints the path. `take --confirm <path>` confirms an unconfirmed lease and runs the slot's deferred reset |
| `upool release [path\|name] [--if-lease-id ID] [--force] [--json]` | Refuses a live session's slot without `--force`; `save_all` then `unity close` for any Editor it opened; `git status`, revert define-order noise, park anything else dirty; otherwise checkout base detached, `git clean -fd`, mark ready; then mirror the project's `.worktreeinclude` files into the free slots (A44) |

| `upool status [--all] [--du] [--json]` | Slots, leases, Editors with their RAM charge, agent worktrees, physical vs apparent disk; `--all` spans every pool |
| `upool open [--headless\|--gui]` / `upool close` | Charge the RAM budget and the cold-import semaphore, wrap `unity open <path>` (with `--args "-batchmode"` for `--headless`, the default, contracts.md A33 and A36) then `unity status --until-ready` (contracts.md A37 to A39); `close` runs `save_all`, `unity close <path>`, and restores `Library/LastSceneManagerSetup.txt` after headless use |

| `upool deinit [--yes]` | The inverse of `init`, run from Terminal inside the repo, dry-run by default: refuses while a slot is leased to a live holder, parked or dirty, or has a live Editor; otherwise removes every slot and clean `agent-*` worktree (`git worktree remove`, no `--force`), the pool's `~/.upool/pools/<repo-key>/` and registry entry, upool's handlers in `.claude/settings.local.json`, an earlier upool's skill copies and marked blocks in files git does not track, warning of any it does (A43), and `.upool.toml`; keeps the `.gitignore` line, every branch and the binary |

State placement is where v1 was wrong twice. v1 put the pool beside the repository and its `state.json` with it; the spike shows the slots belong *inside* the repository, in the app's managed directory, and the state belongs in the home directory, because the two have different readers. The desktop app runs `WorktreeCreate` through `Claude.app/Contents/Helpers/disclaimer`, and from that process `bash` could not open a script under `~/Documents` (`Operation not permitted`), `head` and `getcwd` failed with EPERM, and only `ls -d` and, unexplained, `git` worked (spike §2 T7.6; spike §2 TB); a binary there runs, upool's own included, so upool can be the hook command wherever it is installed (#163). So the hook reads nothing under a TCC-protected folder: the per-pool `state.json` in `~/.upool/pools/<repo-key>/`, the pool registry, the Editor ledger and the one lock over all of them, `~/.upool/lock`, in `~/.upool/`, and the user config at `~/.config/upool/config.toml`. The slots go to `<repo>/.claude/worktrees/slot-N`: a slot there was auto-trusted ("inherited from" the repo), received the app's config overlay, was handed out in 56 to 112 ms against 4,634 ms for a hook-made git checkout, and was reused by a later session once the first was archived (spike §8 A.5; spike §9 E.5; spike §9 E.7). v1's reasons for sibling placement dissolve: APFS `clonefile` needs the same volume, which a directory inside the repo satisfies trivially; the gitignore-clutter complaints were about unignored directories, and `.claude/worktrees` must be gitignored anyway (here `.gitignore:43 .claude/` covers it, and `doctor` checks with `git check-ignore`) (spike §9 E.1); and the docs' refusal of a hook-created directory inside a repository applies only to directories "with no git metadata at all" ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees)). Locking follows both pool tools: each JSON file is rewritten atomically under an OS file lock held only across the read-modify-write, never across a 26 s clone or a 235 s import, with durable ownership in a lease record (random `lease_id`, holder, worktree path, timestamp, `confirmed` flag) ([warmtree on PyPI](https://pypi.org/project/warmtree/); [treehouse README](https://github.com/kunchenguid/treehouse)). Where those tools lock one file, `upool` takes one lock, `~/.upool/lock`, for all of its state: `take` reads the Editor ledger and `release` writes both a pool's state and the ledger, so a lock per file would need a fixed order to avoid deadlock, and a handful of agents doing millisecond rewrites never contend for one lock in practice. `doctor` warns when a pool is on a network or cloud-synced volume, where `flock` is advisory ([flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html)).

Configuration is two TOML files with the precedence every surveyed tool uses, flag, then `UPOOL_*` env, then committed `.upool.toml`, then user config, then defaults, with "unknown keys are errors" as in warmtree ([worktrunk config](https://worktrunk.dev/config/); [clig.dev](https://clig.dev/)). The repo file is optional and carries only data (`ready`, `max_slots`, `base`; contracts.md A30), never commands, because every tool in the space either ignores repo-supplied executables or trust-gates them ([treehouse README](https://github.com/kunchenguid/treehouse)). The defaults change where the spike measured: `ready = 1`; `max_slots = 3`, kept, since disk permits dozens at 0.4 GB each and Editors are the limit; `max_cold_imports = 1`, kept as a cheap default rather than a safety rule; `editor_ram_budget_gb = RAM/4` with `editor_ram_gb = 2.5` and `helper_ram_gb = 2`, from which `max_editors` is derived unless set (3 on this machine); `shrink_after = 14d`; and `agent_ttl = 24h` for the subagent worktree collector (spike §6; spike §8 "What this changes"). Project detection stays a directory containing `ProjectSettings/ProjectVersion.txt` ([editors-install.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/editors-install.md)). The repo file is the human-readable marker that a project is pooled and the thing `init` reads on a fresh clone; the hook never reads it, because `head` on a file under `~/Documents` failed with EPERM from the disclaimed helper, so the hook routes on `~/.upool/registry.json`, which `init` writes from Terminal (spike §2 TB). Distribution is a Go static binary through GitHub Releases and a Homebrew tap, for the reasons in the repository section below ([Homebrew tap docs](https://docs.brew.sh/How-to-Create-and-Maintain-a-Tap)).

## A cloned checkout turns a 235-second cold open into a 38-second first open and a 10-second run

v1 rested on one Windows measurement (155 s cold, 99 s relocated copy, 33 s warm, on a 1.8 GB Library) ([Hissal research §13](https://raw.githubusercontent.com/Hissal/mattpocock-skills-unity/main/research/unity-verification.md)). The macOS numbers are now first-hand, and the gap is bigger. The project `down` has 7,155 tracked files and about 3,400 source assets; its warm Library is 6.5 GB on disk, 6.3 GB apparent, 90,959 files (spike §1). A cold open took **235 s**, imported 12,736 assets, compiled 375 assemblies, grew the Library by 3.8 GB, and peaked at 4.5 GB of Editor RSS with 10 shader compiler processes; the second open took 10 s (spike §2 T4; spike §3). A `cp -cR` of the Library took **15.0 s** and changed free space by −8, +24 and +15 MB across three clones, zero within noise (spike §2 T1.3; spike §4). The first open of a clone at a new path, seeded from a Library current at HEAD, took **38 s with 1 import** (`ProjectSettings/EditorBuildSettings.asset`, which batch mode reimports every run); the second 10 s; an open after one `.cs` edit 11 s with one assembly rebuilt (spike §2 T3b; spike §2 T2 run 2; spike §2 T2 run 3).

The 38 s is not import time, and the spike separated its two causes. `Library/Bee/200b0aEDbg-inputdata.json` embeds the absolute project path 191 times, so any new path rebuilds the Bee DAG, roughly 23 s whether 7 assemblies were compiled (24.3 s) or none (23.0 s) (spike §3). That cost is unavoidable per new path and is the quantitative case for **persistent slots**: a reused slot pays it once, a fresh worktree every time, as v1 argued from the Windows log ([Hissal research §13](https://raw.githubusercontent.com/Hissal/mattpocock-skills-unity/main/research/unity-verification.md)). The second cause is avoidable: `git worktree add` writes `Assets/` with fresh mtimes, so the 7 project assemblies recompile; cloning the working tree keeps mtimes and compiled **0** assemblies, though it saves little wall time because the DAG pass dominates (spike §2 TA). Persistence matters less here than v1's Windows figures implied (about 28 s and 330 MB saved per reuse), but it still decides the architecture (spike §6).

### Why clone the whole checkout rather than check out and clone the Library

v1's recipe was `git worktree add` at base plus an APFS clone of `Library/`. The spike found two costs v1 did not see. A `git worktree add` checkout of this repository costs **about 1,435 MB of real disk per slot** across seven worktrees, so the checkout, not the Library, is the per-slot disk cost (spike §2 T1 extra; spike §4). And a git checkout omits every gitignored file; here `AGENTS.md`, `CLAUDE.md`, `.claude/` and `.agents/` are all gitignored, so a session in a checkout slot loaded none of the project's agent guidance or local settings (spike §2 Follow-up). The whole-checkout clone fixes both: `git worktree add --no-checkout --detach <slot>`, `cp -cR` of each top-level entry except `.git`, `Temp`, `Logs`, `obj`, `Builds` and `.claude/worktrees`, then `git reset -q` to rebuild the index, took 25.9 s (18.2 s clone, 7.7 s index) beside the repo and 24.6 s in the managed directory, cost 47 MB and ≈0 respectively, left `git status` clean, preserved mtimes, and carried the agent files; its first open was 37 s with 1 import and 0 assemblies compiled, its second 9 s (spike §2 TA; spike §9 E.1; spike §3). The 21 symlinks under `.claude/skills/<x>` → `../../.agents/skills/<x>` are relative and resolve inside the slot after `cp -cR`, so no fix-up is needed (spike §10). v1's extrapolation of one to two seconds for a 30,000-file clone was three times too optimistic ([claude-code #93382](https://github.com/anthropics/claude-code/issues/93382)): the measured rate is about 6,000 files per second, so slot creation is a 26 s Terminal-side job and never happens inside a hook. `doctor` verifies physical sharing rather than assuming it ([claude-code #99672](https://github.com/anthropics/claude-code/issues/99672)).

### Why not `unity vcs git worktree add --seed`, symlinks, or the Accelerator

v1 said `--seed` was undocumented and, from one Windows report of "about 7 minutes and 8.2 GB," a byte copy; both were wrong on macOS ([agent-foundry PR #13](https://github.com/furkantokkan/agent-foundry/pull/13)). `unity vcs git worktree add --help` on beta.13 documents `--seed <cache|full|none>`, `--into`, `--no-register` and `--dry-run`, and on APFS it clones: `--seed full` took 18.9 s (14.2 s seeding) for 90,858 files and 6.65 GB, and its first open was 36 s with 322 MB of divergence, the same as the tool's own clone (spike §2 T6.1; spike §2 T6.3; spike §5). `--seed cache`, the default Unity's skill recommends because copying `PackageCache` "finishes *later* than withholding it," is strictly worse here: it withheld `PackageCache`, and its first open re-extracted packages for 51 s and **2.7 GB of real disk** ([version-control.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/version-control.md); spike §2 T6.3; spike §4). The command is still not the pool's primitive, for four measured reasons: it requires a branch (no detached mode), it costs the 1.4 GB git checkout, it registers the worktree with the Hub unless `--no-register`, and its JSON redacts the home directory so a tool cannot use the returned paths verbatim (spike §2 T6.2; spike §5). If the tool ever wraps it, it passes `--seed full --no-register`, never `cache`. Sharing one Library by symlink stays ruled out, since only one instance can hold a project, guarded by `Temp/UnityLockfile` and the instance files ([Unity Manual: command-line arguments](https://docs.unity3d.com/6000.5/Documentation/Manual/EditorCommandLineArguments.html)), and the Accelerator remains an optional passthrough (`unity config accelerator <host:port>`) that cannot shorten the Bee rebuild that is now the whole first-open cost ([Accelerator caching](https://docs.unity3d.com/6000.5/Documentation/Manual/accelerator-caching.html)).

### Slot lifecycle: seed only from a Library current at HEAD, refresh on handout, reset without `-x`

The spike's first three clones each reimported 10 assets instead of 1, and the cause was the seed, not the clone. The main checkout's Editor had been open overnight, unfocused, and never refreshed: `#237`'s `.cs` files were written at 22:44 but `Library/ScriptAssemblies` dated from 21:58, so every clone inherited 9 prefab reimports and 7 assembly recompiles, and when main was next opened it recompiled exactly the 2 assemblies that commit touched; a clone taken after that refresh gave the 1-import result (spike §1; spike §2 T2 run 1; spike §2 T3.3; spike §2 T3b). The seeding rule is therefore: clone only from a Library known to be current at HEAD. `unity cache key` cannot tell: its key was identical before and after a `.cs` edit, because it hashes only the Editor version, `packages-lock.json` and the build target (spike §8 D.1). Staleness is detected the way the spike found it, by comparing the newest mtime under `Assets/**/*.cs` with `Library/ScriptAssemblies`, or with the Editor's DAG in the build cache, `Library/Bee/artifacts/<hash>E….dag/`, where that is newer: the build writes an assembly there on every compile but copies it into `ScriptAssemblies` only when its content changed, so a checkout that gives scripts new mtimes and no new content leaves `ScriptAssemblies` behind however often the Editor compiles (#144). The check also reads the seed source's `git rev-parse HEAD` and a dirty check; the cache key is kept for the Editor or package change that forces a large reimport (spike §8 "What this changes"). A stale source is refreshed before cloning: with an Editor running, `unity recompile` returns `up_to_date` in 0.25 s or does the work, and an `AssetDatabase.Refresh()` eval took 1.73 s cold and 0.30 s warm; with no Editor, a 16 s batch open suffices (spike §8 D.2; spike §2 T3.3). The first slot seeds from the main checkout with its Editor closed; later slots seed from the freshest ready slot, which by definition holds no Editor. After a clean exit `Library/EditorInstance.json` and `ProtocolInstance.json` are already absent and `Library/Pipeline/` survives with one file; the tool still strips all three if present, since on Windows the instance files made `unity test` refuse with "already open in a running Editor" (spike §2 T1.5; [Hissal research §13](https://raw.githubusercontent.com/Hissal/mattpocock-skills-unity/main/research/unity-verification.md)).

A slot's life is then: clone at base, detached; mark ready; on `take`, check out the requested branch and lease; before each handout, mirror into the free slots the gitignored files the project's `.worktreeinclude` names, because a slot freezes a snapshot of gitignored config at clone time (the slot's `settings.local.json` carried probe hooks from clone day) and the app's overlay only fills in files the slot lacks (spike §8 D.4; spike §9 E.5; contracts.md A44); on `release`, close any Editor the tool opened there, check out base detached, and `git clean -fd`. The `-fd` without `-x` is the mechanism every pool tool uses, because `Library/` is gitignored, which `doctor` enforces with Unity's own check, `git ls-files | grep -c '^Library/'` must print 0 ([dcrousso/worktree-pool](https://github.com/dcrousso/worktree-pool); [SKILL.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/SKILL.md)). The tool sets `UNITY_SKIP_HOOKS` for its own git calls so Unity's managed git hooks cannot hang a reset, `refresh --fetch` moves idle ready slots to `origin/<base>` so the Editor reimports only the delta (one `.cs` edit, one assembly, 11 s) (spike §2 T2 run 3), and the tool never prunes inside a live Library.

Two kinds of churn were observed and get one rule each. After a 19.5-hour headless session plus a refresh, clone1's `ProjectSettings/ProjectSettings.asset` came back with `scriptingDefineSymbols` reordered (same set); batch, GUI and headless-plus-refresh runs in the later repro all left the slot clean, so this is rare but real (spike §8 D.3; spike §9 G.1; spike §9 G.2). `release` treats a `ProjectSettings.asset` diff whose only change is the order of `scriptingDefineSymbols` as noise and reverts it; any other tracked change parks the slot. Separately, a headless Editor closed gracefully writes `sceneSetups: []` into `Library/LastSceneManagerSetup.txt`, so the next GUI open in that slot showed an Untitled scene, while batch `-quit` and GUI runs keep the list (spike §8 C.3; spike §9 G.3). `upool close` saves that file, under `~/.upool/pools/<repo-key>/` (contracts.md A8), before a headless session and restores it after, and the skill tells agents to open their scene explicitly.

### Disk: 0.4 GB per persistent slot; disk is not what limits the count

v1 could only bracket slot cost between "whatever the Editor rewrites" and a full copy. Measured: the whole-checkout clone costs 47 MB or less; the first open at a new path diverges **321 to 337 MB** (`Bee` 230 MB, `ArtifactDB` 97 MB, `SourceAssetDB` 35 MB rewritten); later warm opens diverge about zero (free space rose by 41 MB and 7 MB) (spike §2 T2 F2→F3; spike §2 T2 F3→F4; spike §4). A persistent slot is therefore about **0.4 GB**, against 1.8 GB with a git checkout and 3.8 GB for a cold-imported one (spike §4). With 492 GB free, disk does not limit slot count, and `max_slots = 3` stays a count sized by Editors and RAM, not derived from disk (spike §6). The growth failures to design against remain the unbounded pools without visibility: 764 orphaned subagent worktrees at ~36 GB, 72 GB of desktop-app worktrees in two days ([claude-code #58914](https://github.com/anthropics/claude-code/issues/58914); [claude-code #92078](https://github.com/anthropics/claude-code/issues/92078)). `upool` bounds growth by `max_slots`, an optional `max_disk` with LRU removal of idle ready slots, `shrink_after`, and `agent_ttl`; `status --du` reports each slot's private size, the blocks no other clone shares, since a clone's apparent size is meaningless and `du` counts shared blocks in full (contracts.md A32); and `prune` is a dry run unless `--yes`, with no override flags: parked and unmerged slots are left to a person (contracts.md A31) ([dcrousso/worktree-pool](https://github.com/dcrousso/worktree-pool)).

## Editors: budget by RAM, serialize cold imports as a courtesy, target by variable and by path

v1's governance rested on the Windows finding that concurrent cold imports crashed 3 of 4 Editors on a 15 GB machine with shader-compiler out-of-memory errors ([Hissal research §13](https://raw.githubusercontent.com/Hissal/mattpocock-skills-unity/main/research/unity-verification.md)). That did not reproduce: two concurrent cold imports took 259 s and 258 s against 235 s solo (+10 %), peaked at 4.2 GB RSS each with 20 shader compiler processes and 12.5 GB of total Editor RSS, and both exited 0 (spike §2 T5.5). The mechanism v1 described is still visible, one `UnityShaderCompiler` per core, which is why 16 cores and 15 GB died and 10 cores and 64 GB did not ([Unity Discussions: shader compiler processes](https://discussions.unity.com/t/option-to-limit-unity-shader-compiler-processes/914306); spike §2 T4). `max_cold_imports = 1` stays as a cheap default rather than a safety rule: clone seeding makes cold imports rare and serializing them costs almost nothing (spike §6). The steady-state numbers size the budget. Three warm batch Editors ran concurrently at about 1.43 GB RSS each, 5.9 GB total, with no slowdown (spike §2 T5). Idle GUI Editors settled at 1,918 and 1,802 MB after three minutes, about 6.0 GB total with helpers; idle headless Editors grew to 2,294, 1,938 and 1,934 MB after 19.5 hours (spike §8 C.1; spike §8 B.5). So `max_editors` is no longer a count of 2 but a derived value: the ledger charges each long-lived Editor 2.5 GB, a cold-importing one 4.5 GB instead while the import runs (contracts.md A9), and 2 GB for helper processes once any Editor is up, against `editor_ram_budget_gb`, which defaults to a quarter of physical RAM; at 64 GB that admits three Editors with headroom for one cold import, and the user raises it after measuring (spike §8 "What this changes"). v1's plan to gate on `memory_pressure` is dropped: it reported 92 to 93 % free throughout, even under 12.5 GB of Editor RSS, so counting in the ledger is the only workable gate (spike §6). Licensing is still not the constraint for one developer: three Editors ran under one licence here; paid-seat behaviour is untested, so `doctor` reports `unity license status` and enforces nothing ([Unity Manual: Activation FAQ](https://docs.unity3d.com/Manual/ActivationFAQ.html); spike §8 B.1).

Targeting is where v1 trusted the documented resolver too much. The CLI resolves `--project-path`, then "the running Editor whose project directory contains the current working directory," then fails `AMBIGUOUS_EDITOR` ([integration-advanced.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/integration-advanced.md)). Measured: with exactly one Editor running, cwd is ignored, and `unity command eval` run from `/tmp` *and from inside clone2, which had no Editor,* executed in clone1's Editor; with three Editors up, cwd works and `/tmp` gets `AMBIGUOUS_EDITOR` (spike §2 T6.4; spike §8 B.2). `UNITY_PROJECT_PATH` fixes this where it is honoured: it beats cwd, it fails loudly when no Editor matches (`COMMAND_FAILED: No Pipeline instance found for project …clone2`) rather than falling back, and inside a desktop session with the variable exported `unity status` listed only that slot (spike §8 B.2; spike §2 T6.4; spike §8 B.4). But it is honoured only by `command`, `status`, `recompile`, `list`, `job`, `mcp` and `open`, as the beta.13 notes say; `unity test`, `run` and `build` fail at once with "Not a Unity project (ProjectVersion.txt not found at /private/tmp)" when run from `/tmp` with the variable set, their help shows only a positional `[project]`, and `close` and `cache key` are positional too ([Unity CLI release notes](https://docs.unity.com/en-us/unity-cli/release-notes); spike §2 T6.6; spike §8 B.3; spike §8 D.1). `unity run <path> --command` reaches a live Editor rather than booting one (spike §8 B.3). The rule for the tool and the skill is both: export `UNITY_PROJECT_PATH=<slot>` into every session, and pass `"$UNITY_PROJECT_PATH"` positionally to `test`, `run`, `build`, `close` and `cache key`. The batch Editor was listed in `unity status` as `ready` on port 7800, which settles v1's doubt about whether batch Editors appear at all, so headless readiness uses `status --until-ready`, not a `unity command` probe (spike §2 T6.4).

The Editor lifecycle the tool wraps has measured edges. GUI Editors were ready in 11 to 21 s, headless ones within 57 s (spike §8 C.1; spike §8 B.1). Readiness is `unity status --until-ready --timeout N --format json`: for a non-existent path, or a project with no Editor, it waits the **full timeout** (15.1 s at `--timeout 15`) and then exits 6 with `STATUS_NO_INSTANCES`, so it is a wait-for-boot primitive, and `upool open` pairs it with a PID check so a crashed launch fails before the timeout (spike §2 T6.5). The first `eval` on a freshly opened GUI Editor timed out at 5,000 ms yet ran; later evals took 0.17 to 0.31 s, so after a first-call timeout the wrapper re-queries for side effects instead of retrying blindly; for `save_all`, the re-query is a second `save_all`, which changes nothing once the first has run (spike §8 C.3; contracts.md A29). `unity close` on a GUI Editor with a dirty scene closed gracefully in 12.1 s with **no dialog, even without `-automated`,** and the scene file was unchanged: the work was discarded, as the help text "exits without saving" warns (spike §8 C.4). `unity command save_all` returned `saved: true` in 0.73 s and a following `close` took 0.99 s, leaving the edit on disk, so release is always `save_all` then `close`; `close` with the positional path hit the right PID with two GUI Editors up and with three headless ones (spike §8 C.5; spike §8 C.6; spike §8 B.5). An unfocused GUI Editor throttles updates until `set_autotick` is enabled, which is why the overnight main Editor never refreshed ([playmode-verification-loop.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/playmode-verification-loop.md); spike §1). Crash recovery stays conservative: only when the ledger's PID is dead and `unity status` reports nothing may `doctor --fix` delete that slot's `Temp/`, since a leftover `UnityLockfile` is the documented cause of "project is currently open" errors ([Unity Support: project is currently open](https://support.unity.com/hc/en-us/articles/40828087523092-Resolving-the-The-project-is-currently-open-in-the-Unity-Editor-Please-close-it-in-the-Editor-to-proceed-with-this-operation-Error)). `unity test <path> --mode EditMode` booted its own batch Editor and passed 3 of 3 in 70 s on a warm clone, the price of its separate boot; a slot with a resident Editor should test through blocking `unity recompile` plus `unity command run_tests`, never the non-blocking `unity command recompile` (spike §2 T6.6; [build-run-test.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/build-run-test.md)).

## Hooks route, skills teach, leases and lanes keep agents from colliding

Anthropic's own doc draws the line that decides the integration design: `CLAUDE.md` files are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead," and warmtree's author found that without an instruction block agents "keep running `git worktree add` from habit" ([Claude Code memory](https://code.claude.com/docs/en/memory); [warmtree on PyPI](https://pypi.org/project/warmtree/)). `upool init` registers hooks in the project's `.claude/settings.local.json`, and the hooks carry the instructions: `upool hook session-start` gives a session in a slot the block and the skill's body as `SessionStart` context on every start, and `upool hook subagent-start` gives its subagents the same as `SubagentStart` context, so that no file of the project's has to hold them (contracts.md A43). The marked block `init` upserted into `CLAUDE.md` and `AGENTS.md`, and the skill it installed at `.claude/skills/upool/SKILL.md` and under `.agents/skills/`, are retired by A43: `init` and `deinit` take them out of a file git does not track and warn of one it does, writing into no tracked file ([Claude Code skills](https://code.claude.com/docs/en/skills)). Registered there, the desktop app runs the hooks but skips its config overlay and auto-trust for the worktree, because the "hook came from a repo-committed settings tier … (provenance not vouched)"; at user scope the same hook cleared that check, but would run in every repository on the machine. upool chooses the project: what the overlay would copy, a project lists in its `.worktreeinclude`, which upool mirrors into the slots (contracts.md A44), and what the skipped auto-trust costs is being measured (spike §2 TB; spike §8 A.5; contracts.md A26). The skill's body is short and operational (the per-command targeting rule, "`save_all` before `close`," "never hand-edit scene YAML while a live Editor is reachable," "after a first-call timeout, re-query before retrying"), restating Unity's own rules so they travel into subagents, which do not inherit invoked skills ([SKILL.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/SKILL.md); [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)).

### Route Claude Code's worktrees through the pool: three branches in one hook

`WorktreeCreate` "replaces the default git behavior," the command hook must "print the worktree path on stdout," and any non-zero exit fails creation; `WorktreeRemove` fires when such a worktree is removed ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). The spike settles what v1 listed as open. The desktop app fires `WorktreeCreate` (v1 could only hope so), from a `disclaimer` helper whose only tested capabilities under `~/Documents` were `ls -d` and `git`, and it fires `WorktreeRemove` one second after archive (spike §2 T7.6; spike §2 TB; spike §8 A.6). The CLI's `claude -p --worktree` fired it too (spike §2 T7.4). The stdin contract is `{session_id, transcript_path, cwd, hook_event_name, name}` (spike §5). A failing hook aborts the session with `worktree_hook_failed` and no fallback, observed four times (spike §8 A.7). And because a hook has no matcher, it replaces worktree creation for every repository whose settings register it and every kind of request there, which the spike demonstrated when a user-scope hook caught this repository's subagents (spike §9 "What this changes"). upool's hooks are therefore registered per project, by `init`, so they run only in the projects upool pools (A26).

The hook therefore branches three ways on stdin fields alone, since the disclaimed process cannot read the repository. A **subagent** request carries `prompt_id` and `scratchpad_dir`, which session requests lack, a `name` of the form `agent-<17 hex>`, and arrives from the bundled CLI process with full file access (spike §9 F.2; spike §9 F.3; spike §5). These never get a pool slot, because **no `WorktreeRemove` ever arrived for them**, not when the subagents finished and not when the session was archived; both worktrees were still on disk and registered afterwards (spike §9 F.3). The hook gives them an ordinary `git worktree add --detach <repo>/.claude/worktrees/<name>` (what the app would have made itself), prints the path, and records the parent `session_id` and the creating process's parent PID; `prune` collects such a worktree when it is clean and its parent process is gone or it is older than `agent_ttl`. A subagent that needs Unity asks for a slot through an explicit `upool take` and releases it itself. A **pooled session** request (`cwd` matches a pool in `~/.upool/registry.json`, no `prompt_id`) gets a free ready slot: the hook calls `upool take --no-create --holder <session_id> --timeout 20`, prints the slot path with every other byte on stderr, and records the lease as *unconfirmed*. The desktop's `session_id` here is the app's own id and differs from the `session_id` the CLI reports in `SessionStart`, and `name` is generated from the first prompt (`env-project-status-6b702e`), so leases are correlated by worktree path and `name` is a hint only (spike §2 TB; spike §8 A session ids). The app enforces one live session per path itself: four handouts of a slot already in use were refused with `hook printed "…/slot-1", which is already in use by worktree "…"` and no `WorktreeRemove` followed, so a lease recorded at create time would leak; this is why the lease starts unconfirmed and expires unless `SessionStart` confirms it (spike §8 A.7; spike §9 E.7). A session that is in no pool, such as one started inside a slot (A13), gets the pass-through branch: `git -C <cwd> worktree add <cwd>/.claude/worktrees/<name>` and its path printed, the worktree Claude Code would have made; git ran from the disclaimed helper in every test, but this branch was never exercised on a second repository (spike §2 TB; spike §9 H).

Three consequences of the managed-directory placement shape what the hook may rely on. The app registers the lease in `~/Library/Application Support/Claude/git-worktrees.json` and deletes that entry on archive; subagent worktrees never appear there (spike §9 E.4; spike §9 Registry). The app's `untrackedDirGc` never sighted `slot-1` across two relaunches; its trigger is unknown and the inference that it targets unregistered directories is not an observation, so `doctor` and every `take` check that each slot is still on disk and in `git worktree list` (spike §10; [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)). And the app accepts `WorktreeRemove` exit 0 with the directory still present: it logged "Removed hook-based worktree," deleted its registry entry, and handed the same path out again 10 s later, which is the whole reuse mechanism (spike §8 A.6; spike §8 A.7; spike §9 E.6). Dirty slots are parked, not refused, and the need is now measured: a session that created an untracked file was archived with **no warning**, the remove hook saw `?? spike-reuse.txt`, and nothing else would have protected it (spike §8 A.8). The remove hook runs `git status --porcelain` in the slot (which worked from the disclaimed helper), applies the define-order noise rule, quarantines a dirty slot as `parked` (unleased, not ready, never reset) for `prune` to surface, marks a clean one `needs-reset`, and exits 0 either way; no surveyed tool deletes unmerged work or auto-commits ([treehouse README](https://github.com/kunchenguid/treehouse); spike §8 A.6).

### Environment, confirmation and release

`SessionStart` is the hook with file access, and the spike moved most of the per-handout work there. It runs in the CLI process (`getcwd` succeeded under `~/Documents` even for worktree sessions), its stdin `cwd` is the slot, and its process cwd is the **repository** even then, so the script reads stdin `cwd`, never `$PWD` (spike §2 TB). Project-level hooks for a slot session come from the **main checkout's** `.claude/settings*.json` and run with the main checkout as cwd; markers placed in the slot's own `settings.json` and `settings.local.json` never fired across five sessions, so a slot's copies are inert and nothing runs twice (spike §8 A.5; spike §9 E added hook source). The project's `SessionStart` hook calls `upool take --confirm "$cwd"`, which confirms the lease by path, runs the deferred reset if the slot is marked `needs-reset`, appends `export UNITY_PROJECT_PATH=<slot>` to `CLAUDE_ENV_FILE`, which reached the Bash tool in both the CLI and the desktop app on 2.1.295, and spawns a detached `upool refresh` to top the pool back up to `ready`, since a 26 s clone cannot run inside the disclaimed create hook (spike §9 E.5; spike §2 T7.5; spike §8 A.5). That refresh, and `upool release`, also mirror the gitignored files the project's `.worktreeinclude` names into the free slots, ahead of the next handout: the overlay skips files already present, so stale copies are the tool's problem, and the confirm is too late to copy them, since Claude Code has read `CLAUDE.md` and its imports before `SessionStart` runs (contracts.md A44). Auto-memory follows the repository, transcripts are keyed by the slot path, and `CLAUDE.md`/`AGENTS.md` come from the slot; v1's citation that a hook-created worktree "keeps its transcript at the launch directory" did not hold (spike §9 E added memory; spike §5). `WorktreeRemove` is the release for the desktop app and for an interactive `claude --worktree` session, whose `/exit` sends it; upool registers no `SessionEnd` hook, since its stdin names no slot and every captured session end is already released ([contracts.md](contracts.md) A25). CLI `-p` sessions never fire `WorktreeRemove`, so for them, and for Codex, Cursor, Gemini and Copilot, which have PreToolUse-style hooks but no worktree event, the `upool run <name> -- <agent>` launcher's take, export, run, release-on-exit is the only release, with the dead-PID reclaim behind a session that bypasses it (spike §2 T7.5; [Codex hooks](https://learn.chatgpt.com/docs/hooks); [Cursor hooks](https://cursor.com/docs/agent/hooks)).

### Leases that survive crashes and never reclaim a live tree

The data-loss failures in the issue trackers share one cause, a reset that judged liveness by the wrong signal: the desktop app's pool detached a live session's HEAD on a `pooledAt` timestamp, and a SIGKILLed treehouse command left `HEAD.lock` files that made "10 of 10 'available' slots" unusable while `status` said available ([claude-code #75911](https://github.com/anthropics/claude-code/issues/75911); [treehouse #161](https://github.com/kunchenguid/treehouse/issues/161)). `upool`'s rules are the inverse. State is written before `git worktree add` as an "acquisition incomplete" entry and the `.git` file's gitdir backlink is authenticated before any slot is trusted; liveness is the lease (random `lease_id`, worktree path, holder id, holder PID with start time, `confirmed` flag), and nothing else. The lease takes no `git worktree lock`, though Claude Code holds one on its own trees "so that concurrent cleanup can't remove it" ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees)): the desktop app refuses to archive a locked worktree and never runs `WorktreeRemove` for it (contracts.md A27), and a one-second poller saw the app never lock or touch a hook-made slot (spike §8 A.4). Reclaim happens only when the holder PID is dead *and* the ledger shows no live Editor in the slot *and* the tree is clean; a dead holder with a dirty tree becomes `parked`; an unconfirmed lease older than `confirm_timeout` (default 60 s) is simply released, since the app refuses a second session on the path anyway (spike §8 A.7). `take` prints why each slot was skipped (`creating`, `warming`, `leased`, `unconfirmed`, `parked`, `editor-running`, `missing-from-worktree-list`; a `needs-reset` slot is handed out when no slot is ready, and reset as its lease is confirmed, per contracts.md A5) ([treehouse #162](https://github.com/kunchenguid/treehouse/issues/162)). Pool-full is a wait, not a failure: `take --timeout S` retries once per second, which inside the create hook means the app's session start waits up to 20 s and then aborts with a stderr message naming `upool refresh`; growth stops at `max_slots` ([dcrousso/worktree-pool](https://github.com/dcrousso/worktree-pool)).

### Lanes: scripts in parallel, scenes one at a time, `.meta` never regenerated

Every Unity-specific practitioner converges on the same partition: "Two jobs that own the same folder never run at the same time," script jobs in parallel, "scene, prefab, and shared-asset work one lane" ([siiplasplas/unity-parallel-agents](https://github.com/siiplasplas/unity-parallel-agents)); Mirven's version is "Scenes and assets take turns" ([mirven.app](https://mirven.app/)). `upool` encodes this as a `lane` attribute on the lease, `script` (default, unlimited) or `scene` (exactly one per project). Enforcement is a `PreToolUse` hook, registered by the project as its other hooks are (A26), on `Edit|Write|NotebookEdit` that reads the lane via `upool which --json` on the tool's file path and denies writes to `*.unity`, `*.prefab`, `*.asset` and `*.meta` in script lanes, with `"onFailure": "block"` so a failed hook denies rather than silently allowing ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). The documented hole stays documented: none of the isolation checks "tracks which files a shell command writes," so `cp` and redirects into other lanes are not refused ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees)). The GUID rule is hygiene the tool verifies rather than invents: Force Text serialization, Visible Meta Files, `.meta` committed with assets, because "Branches that create or move the same asset get different GUIDs" ([siiplasplas/unity-parallel-agents](https://github.com/siiplasplas/unity-parallel-agents)). `init` runs none of Unity's VCS set-up: `vcs doctor --fix` moves a project's binaries to LFS and installs git hooks, so `doctor` reports what `unity vcs doctor` finds and the commands to run instead (contracts.md A35). Before release it runs `unity projects verify --strict`, which "needs no Editor, license, or network access", and warns on a failure without holding the slot (contracts.md A34) ([version-control.md](https://github.com/Unity-Technologies/unity-agent-plugin/blob/main/skills/unity-cli/references/version-control.md)). "Done" is a headless gate: `unity recompile`, then `unity test "$UNITY_PROJECT_PATH" --affected --since <base>` per lane, with `unity build` at merge time ([Unity CLI release notes](https://docs.unity.com/en-us/unity-cli/release-notes)).

## What remains unverified

The spike confirmed the clone economics, the managed-directory placement, the hook contracts, the per-command targeting rules, save-then-close, the RAM figures and the registry behaviour, so those leave the test list. What is left is untested or inferred.

- **Pass-through on a second repository.** Skipped because no other repository is set up in the desktop app; git ran from the disclaimed helper in every test, but a non-pooled repo under `~/Documents` has not been tried (spike §9 H; spike §2 TB).
- **Git writes and `unity` calls from the disclaimed helper.** Only `git worktree add` (under `~/.upool-probe`) and `git status` (under `~/Documents`) were exercised; `git checkout --`, `git clean -fd` and a `save_all`/`close` from the `WorktreeRemove` hook are untested, which is why the reset is deferred to `SessionStart` and the remove hook only reads and marks.
- **`untrackedDirGc`.** It left a registered slot alone across two relaunches and its trigger is unknown; "it targets unregistered directories" is an inference from the name (spike §10).
- **Logged-in CLI flows.** `claude --worktree` interactive sessions, `/batch`, `WorktreeRemove` timing from the CLI, `SessionEnd`, `CwdChanged`, and the lane `PreToolUse` guard were not run; the CLI was not logged in (spike §8 A.9).
- **Why a slot's own project hooks never ran.** Observed across five sessions with the repo's hooks running instead; the reason is unconfirmed (spike §8 A.5).
- **Subagent worktree liveness.** Collecting `agent-*` worktrees by parent-process liveness assumes the subagent create hook's parent PID is the session's CLI process, which follows from where the hook ran but was not checked (spike §9 F.2).
- **GUI memory under Play mode and long interactive use.** Only idle Editors were measured; confirm the 2.5 GB charge under real use before going past three Editors (spike §8 C.1; spike §8 B.5).
- **Seeding from a running source, or from a slot.** All clones came from the main checkout with its Editor closed; cloning while its Editor is open, the CLI's reported refusal to seed in that state, and cloning from a ready slot are unmeasured (spike §1).
- **Larger Libraries.** This Library is 6.3 GB and 91k files; clone time scales with file count, and the 36 GB `Artifacts` cases in the issue trackers are untested ([Unity Discussions: Cleaning Library](https://discussions.unity.com/t/cleaning-library-folder/828619)).
- **Windows and Linux.** Nothing was measured; v1's Windows evidence (robocopy timings, the 3-of-4 crash, path-length failures) is the only data ([Hissal research §13](https://raw.githubusercontent.com/Hissal/mattpocock-skills-unity/main/research/unity-verification.md)).
- **Pro, floating and Build Server licences.** Three instances ran under one licence here; paid-seat behaviour with several instances is untested ([Unity Manual: License overview](https://docs.unity3d.com/Manual/LicenseOverview.html)).
- **Resident-Editor testing.** `unity test` refusing a slot whose Editor is open and the `run_tests`/`test_status` path were not exercised on macOS (spike §2 T6.6).

## Build in four phases, with the clone recipe first

**Phase 1, the pool core:** `take`, `release`, `which`, `path`, `status`, `doctor`, with state under `~/.upool/`, the pre-write entry and backlink check, the whole-checkout clone recipe with the instance-file strip, the staleness check against `ScriptAssemblies` plus the cache key, `git clean -fd` reset, lease ids with conditional release and the `confirmed` flag, dead-PID reclaim with parking, the define-order noise rule, `.claude/worktrees` gitignore verification, and the global registry. This alone replaces a shell script and is testable from Terminal with no agent at all. **Phase 2, Claude Code integration:** `init` registering upool itself as the project's hooks in exec form; the create hook's three branches (subagent, pooled, pass-through) with path-only stdout and a 20 s wait; `SessionStart` doing `take --confirm`, `CLAUDE_ENV_FILE` export and the background top-up, which mirrors the `.worktreeinclude` files into the free slots (A44); `WorktreeRemove` doing `git status`, noise revert, park-or-mark and exit 0; the skill, the instruction block and the `run` launcher. Test the pass-through on a second repository before shipping this phase. **Phase 3, Editor governance:** the ledger with the RAM budget and `max_cold_imports`, `open`/`close` around `unity open <path>`, `status --until-ready` with a PID check, `save_all` then `unity close <path>`, `LastSceneManagerSetup.txt` save and restore, the positional-path wrappers, the first-call-timeout re-query, and the lane `PreToolUse` hook with `projects verify --strict` at release. **Phase 4, hygiene:** `refresh --fetch`, `prune --all` with dry-run and the `agent-*` collector, `max_disk` LRU, `status --du`, and the per-project `.upool.toml`.

Leave out, with reasons the evidence supplies: a daemon (no surviving tool has one, and "it is surprising when programs do things in the background" is clig.dev's rule; the one detached job the tool spawns, a top-up after a handout, is announced in `status` and exits when done) ([clig.dev](https://clig.dev/)); self-update (three betas of Unity CLI fixes; `brew upgrade` is free); an MCP server (Unity says `unity command` is "faster and use[s] fewer tokens," and it was reachable from every session with one variable) ([Replace MCP server with Unity CLI](https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli); spike §2 T6.4); wrapping `unity vcs git worktree add`, which costs the 1.4 GB checkout, requires a branch and registers with the Hub (spike §2 T6.2); Accelerator management beyond a config passthrough; scene merging, planning, review and WIP auto-commits; Windows and Linux until the macOS core is dogfooded ([claude-code #91973](https://github.com/anthropics/claude-code/issues/91973)); and repo-level executable hooks of any kind.

## Repository, CI and Homebrew distribution

**Language: Go (decided 2026-10-13).** The binary runs in three places with different budgets: the hook, which the desktop app's disclaimed helper executes at every worktree session start; `which`, `path` and `status`, which agents call between tool steps; and `take`, which clones for 26 s under a lock it must not hold. A static binary starts in milliseconds with no runtime on the machine, which rules out Node (the desktop helper cannot be assumed to have it) and makes Python via `uv` a second choice: `uv` is one more install, and Homebrew packaging of Python tools means vendoring every wheel. Go cross-compiles darwin/arm64 and darwin/amd64 from one `go build`, GoReleaser turns a tag into a GitHub Release with checksums and pushes a Homebrew formula to a tap repository without a hand-written formula, and treehouse is the precedent in this niche ([treehouse README](https://github.com/kunchenguid/treehouse)). Rust would serve equally, at a slower iteration pace for agents writing it. Dependencies stay at a TOML parser, if wanted one CLI framework, and, for tests only, `github.com/rogpeppe/go-internal/testscript`; file locking, JSON, process inspection and `clonefile` via `cp -cR` are stdlib or shell.

**Name: `upool` (checked 2026-10-13).** Free on Homebrew (`brew search upool` returns only the unrelated cask `utools`), PyPI and crates.io. npm has an abandoned `upool` from 2014 ("Job queue pool for each user," 0 stars, last release 0.2.1), which blocks `npx upool` but nothing else; it only matters if an npm install path is ever wanted.

**Layout.** One module, one binary, embedded assets:

```text
upool/
  cmd/upool/main.go                 entry point: main calls run(args, stdin, stdout, stderr, getenv), which tests call in-process; subcommand dispatch, the only writer of stdout
  internal/config/                  .upool.toml + ~/.config/upool/config.toml (never os.UserConfigDir), precedence, unknown-key errors
  internal/registry/                ~/.upool/registry.json, repo keys, pool lookup by stdin cwd
  internal/pool/                    state.json, slots, leases, confirm, park, reset; the slot lifecycle as a pure transition function
  internal/clone/                   whole-checkout clone recipe, instance-file strip, staleness check
  internal/unity/                   one verb table for the targeting rules; wrappers: open, status --until-ready, save_all, close, recompile, test; Response, the lenient reply type
  internal/ledger/                  ~/.upool/editors.json, RAM budget, cold-import semaphore, dead-PID reclaim
  internal/hooks/                   WorktreeCreate/Remove/SessionStart logic; handlers return (path, error) (the shell scripts only exec `upool hook <event>`)
  internal/output/                  JSON envelope, exit codes

  scripts/capture-hook.sh           records hook stdin during a manual gate, then runs the hook it wraps

```

Hooks stay trivial on purpose: each is `upool hook <event>`, registered in exec form by the path `init` found upool at (since `PATH` under the helper is not the user's shell `PATH`), so logic lives in Go where it is tested. No script stands between the hook and upool: the helper cannot read a file under `~/Documents`, so a script there fails, but it runs a binary there, so upool needs no stand-in outside it (#163; [contracts.md](contracts.md) (a)).

Five rules hold the layout together. Every path `upool` compares, a lease's worktree path, stdin `cwd` against the registry, the working directory in `which`, goes through `internal/paths` first: macOS spells one directory as `/var` and `/private/var`, or `/tmp` and `/private/tmp` (the Unity captures show the second), APFS is case-insensitive by default, and the desktop app stores lowercased paths, so a plain string comparison would leak leases. All of `~/.upool/` sits under one lock, `~/.upool/lock` (see the state placement paragraph above). `internal/unity` sends every call through one table that says, per verb, whether it honours `UNITY_PROJECT_PATH` and whether it takes the path positionally, and the slot lifecycle is a pure function from state and event to state; both are tested row by row against `docs/contracts.md` (c) and (f). Hook handlers return the worktree path and an error, and only the dispatcher writes stdout, so nothing else can reach it. Unity CLI replies decode into the lenient `unity.Response`, never into `upool`'s own `output.Envelope`, which stays strict, so a field a new CLI adds cannot leak into `upool`'s output.

**The files that make the repo usable.**

- `README.md`: what it does in two sentences; the quickstart as two commands (`brew install weslo/tap/upool`, `cd <project> && upool init`); how a session gets a slot (five bullets, no internals); requirements (macOS on APFS, Unity CLI 1.0.0-beta.13 or later, Claude Code 2.1.295 or later, git); a CI status badge and a roadmap of the milestones saying which are shipped; links to `docs/design.md` and `docs/contracts.md`. What the tool leaves out is recorded in this document, not repeated there. The README is the only prose an agent reads before trying the tool, so the three commands must be exactly right.
- `LICENSE`: MIT, which every surveyed tool in the space uses.
- `CONTRIBUTING.md`: build and test commands; coding standards for Go, scripts and documentation; the rule that every behaviour against Unity or Claude Code is tested against the fake `unity` (the test binary standing in for the CLI) and the captures under `testdata/captures/`, which are never edited; the test approach (layers, isolation, golden files); and that anything needing a real Editor or the desktop app is a manual gate listed under `docs/manual-gates/`, never a claim in a PR; one PR per issue; CI green before a human review, and a human merges every PR (reviewers may use agents to help them read, but the decision to merge is theirs); no new dependencies without an issue.
- `AGENTS.md`: the guidance every coding agent working on the repository reads, pointing at `CONTRIBUTING.md` for the rules; `CLAUDE.md` only imports it, so Claude Code reads the same text.
- `CHANGELOG.md`: kept by hand under Keep a Changelog headings; GoReleaser reads it for release notes.
- `ci.yml`: on pull requests and pushes to `main`, one job on `ubuntu-latest` and `macos-latest` with the Go version from `go.mod`: `make check-paths`, `make check-captures`, `go vet`, `golangci-lint` (default linters only) and `go test -race -shuffle=on ./...`. On macOS that includes the tests tagged `//go:build darwin` that exercise `cp -cR` sharing, `flock`, and the clone recipe against a temporary git repo. Tests tagged `//go:build unity` need a real Editor and never run in CI.
- `release.yml`: on tag `v*`, GoReleaser with a `HOMEBREW_TAP_TOKEN` secret (a fine-grained token with contents write on the tap repository only). The tap is a second repository named `homebrew-tap` with nothing in it but the generated `Formula/upool.rb`; users run `brew install weslo/tap/upool` and later `brew upgrade upool`. The formula stays a `brews` section, with GoReleaser pinned to a version that supports it, since a cask would install the unsigned binary quarantined (contracts.md A16). Plain `brew install upool` with no tap prefix means homebrew-core, whose notability rules (age, stars, maintained releases) are not met by a new project, so it is a later step, not a launch requirement ([Homebrew tap docs](https://docs.brew.sh/How-to-Create-and-Maintain-a-Tap)).
- Repository settings: squash merges only; branch protection on `main` requiring a pull request and the CI checks `ci (ubuntu-latest)` and `ci (macos-latest)`, and nothing more: no required approval, because GitHub does not let a pull request's author approve it and a one-maintainer repository has no one else to (the human merge is the review); branches need not be up to date with `main` before merging; and administrators, which includes the maintainer and any agent working with the maintainer's credentials, are not bound by it and can push to `main` directly. This is lighter than the plan first set out, deliberately: stricter protection slowed solo agentic work, so it stays this way and is not a gap to close. `CODEOWNERS` stays in place for the day reviews are required. Labels `phase:0` to `phase:4`, `manual-gate`, `blocked`, `decision-needed`; milestones M0 to M4.
- Versioning: `v0.1.0` when Phase 1 passes its manual gate; `v0.2.0` for Phase 2; semver from there. No tag before the gate script in `docs/manual-gates/` for that milestone has been run on a real Mac, but for a release candidate, `vX.Y.Z-rc.N`, tagged on the commit the gate runs so that the gate can install from the tap, which is empty until a release writes its formula; `vX.Y.Z` follows once the gate passes, on the release's own commit, which names it in `CHANGELOG.md`, as `v0.3.0` did (maintainer decisions, 2026-10-22 and 2026-10-23, on #106).

## Appendix A: execution plan from a blank repository

The plan assumes nothing but an empty GitHub repository, the two documents from this design effort, the spike's `logs/` folder, and a Mac with Go, `gh` and `git` installed. It runs in four stages. Stage 0 is ten minutes of human setup; stage 1 is one agent session that makes the repository a repository; stage 2 is one agent session that turns the design into milestones and issues; stage 3 is the per-issue loop that runs until the milestones are empty, with a human gate at the end of each milestone. Each agent stage is a prompt below, written to be pasted as the first message of a fresh session in the repository.

### Stage 0: human setup

1. Create the empty **public** repository `weslo/upool` on GitHub (no README, no license; the bootstrap agent writes them so they match the docs). Public keeps branch protection, macOS CI minutes and the tap free of plan and token requirements. Create a second empty repository `weslo/homebrew-tap`; it stays empty until M4.
2. Clone `upool` wherever your projects live; `~/Documents/...` is fine. The `~/Documents` restriction the spike found applies only to files the hooks read, the pool state, which upool keeps under `~/.upool/`; the helper runs a upool built in the checkout (#163), and the pooled Unity projects themselves were under `~/Documents` throughout the spike.

## Conclusion

The spike reframes the problem once more. v1 said the expensive thing is the first open of a worktree; that holds, with the cost now split precisely: asset import is solved by cloning (12,736 imports became one, in 15 s and no disk), script compilation is solved by cloning the working tree instead of checking it out (7 assemblies became none), and the ~23 s that remains is a Bee DAG rebuild keyed on the absolute path, which only a persistent slot avoids. The surprise is where the disk went: not the 6.3 GB Library, which clones for free and diverges by 330 MB once, but the 1.4 GB git checkout, which the whole-checkout clone replaces with 47 MB.

The second shift is in what the host applications actually do. The desktop app fires `WorktreeCreate`, trusts an exit-0 remove, refuses a path that is in use, warns about nothing on archive, grants trust and overlay only inside `.claude/worktrees`, runs the hook from a helper that cannot read `~/Documents`, and never removes a subagent's worktree. The Unity CLI honours `UNITY_PROJECT_PATH` for seven verbs and ignores it for five, misroutes on cwd when one Editor is up, waits out its timeout before saying no Editor exists, and discards unsaved scenes without a dialog. None of this is in the documentation, all of it is now measured, and each item maps to one rule: slots in the managed directory, nothing the hook reads under `~/Documents`, leases confirmed on `SessionStart` and correlated by path, throwaway worktrees for subagents, `git status` before any reuse, the variable exported and the path passed positionally, `save_all` before `close`, and a RAM ledger instead of a memory-pressure sample. The tool's job is still to honour a few contracts precisely and refuse the features that would make it the thing that needs managing; the contracts are just more specific, and better evidenced, than v1 could make them.
